## 2. 首版页面结构

视觉采用暖白底、莓果色主按钮、少量桃粉与浅蓝作为分区辅助色；依靠清晰文字和小图标营造温馨感。正文至少 16px，常用控件约 44px 以上，底部避开手机安全区域；支持系统字号与页面缩放。

| 底部入口 | 首屏优先内容 | 主要操作 |
| --- | --- | --- |
| 今天 | 当前阶段、今日预约/待办及完成情况、快速记录 | 记血糖、记体重、写备忘；完成事项；查看近期安排 |
| 记录 | 日期切换、当日记录、历史入口 | 新增/补记/修改/删除；按情境查看血糖趋势、体重趋势 |
| 日程 | 月历与所选日期的纵向清单 | 看未来安排、添加预约/个人事项、处理建议窗口 |
| 指南 | 日常问题搜索、阶段筛选、主题筛选 | 阅读结论、做法、注意事项与来源；交叉跳转 |
| 我的 | 孕程与医生要求、地区/单位、数据说明与备份 | 日期影响预览、分娩确认、导出、恢复、历史资料 |

“今天”往下显示未来 7～14 天的重要安排和 2～3 篇相关指南。没有资料时直接开放记录与检索，顶部提示补充阶段；不展示假孕周、示例预约、示例血糖或“0 kg”。

每篇指南使用一个稳定 ID，同时关联多个阶段和主题。阶段暂按早期至 13+6、中期 14+0～27+6、晚期 28+0 起组织阅读；产后从实际分娩日期计算。内容的具体适用窗口可窄于分类范围。产后一个月按“实际分娩日加一个日历月”界定，分娩当天显示“分娩当天”，次日为“产后第 1 天”。超过一个月显示已超出本期内容覆盖范围，保留记录和日程，不自动启用育儿建议。

### 核心操作流程

1. **快速记血糖**：首页点“记血糖” → 数字键盘填数值 → 选择空腹/餐前/餐后 1 小时/餐后 2 小时/睡前/其他 → 保存。日期与时间可调整以补记；明确单位，餐前/餐后可附早餐、午餐、晚餐或加餐。首次不猜测测量情境，后续记住用户选择并保持可见。
2. **看记录与趋势**：点记录可修改或删除；在趋势页先选测量情境，再看曲线。不同情境不混算均值，空值不转零。记录原始单位；必要时提供明确标注的统一显示单位，不能把旧 GL 转成血糖。
3. **看今天/某一天**：以类型标签区分预约、个人事项、建议窗口，同时显示当天体重、血糖和备忘。完成状态由用户勾选；有记录不自动代表已完成医生要求。
4. **把建议变成预约**：打开建议窗口 → 用户输入医院确定的日期/时间 → 新建独立预约并关联原建议。预约既不等同建议，也不受改预产期自动移动。
5. **找答案**：输入“便秘怎么办”“水果能不能吃”等 → 对真实指南标题、摘要、正文和同义词检索 → 可同时筛阶段与主题 → 展开全文并查看来源和审核状态。无结果时如实显示，不现场生成医学答案。
6. **改日期**：“我的”修改日期 → 显示将移动、保留与需核对的事项 → 确认 → 保存修改历史。预览期间新增记录时，旧预览作废，要求重新查看，避免覆盖新记录。

## 3. 必要功能与后续范围

### 本期必要

- 今天、记录、日程、指南、我的互相联通，手机优先，桌面兼容。
- 体重、带时间/单位/情境的血糖、多条备忘与身体感受、个人待办；所有字段按记录类型填写，不做每日整套必填。
- 新增、补记、修改、删除、历史查询、同情境趋势；编辑和删除有明确反馈。
- 月历＋按日清单；三种事项类型、完成情况、近期安排、日期调整与实际分娩的确认流程。
- 资料去重、日常说法检索、阶段/主题交叉分类、来源与更新时间。
- 孕前已确诊二型糖尿病与妊娠期糖尿病分开标注；医生要求由用户输入并保留生效时间，不预填个人目标、频次或用药方案。
- 保留旧数据、迁移预览、备份恢复和存储失败提示；按确认的方案实现本机保存或登录同步。

### 可选轻量记录纳入首版

| 内容 | 首版处理 | 理由 |
| --- | --- | --- |
| 饮食 | 可选记录餐次和吃了什么，保留旧饮食历史 | 可帮助回忆血糖前后的进食，不强迫称重算热量 |
| 活动 | 可选类型、时长和感受 | 可用于复诊交流，不用运动消耗作为每日达标指标 |
| 用药 | 可选记录实际药名、剂量文字、时间；医生要求另行保存 | 二型糖尿病管理有实际用途；不自动建议加减药、不推导漏服补药方案 |

暂不开发 AI 问诊、热量缺口减肥目标、自动诊断、从读数推导治疗计划、食物图片识别、设备连接、完整宝宝育儿模块或后台手机推送。站内清单不是站外通知；首版不展示没有真实触发能力的“开启提醒”按钮。

## 4. 动态日程规则

| 对象 | 修改预产期时 | 确认分娩时 |
| --- | --- | --- |
| 未开始、未完成的建议窗口 | 用确认日期及已核验模板重算；预览后应用 | 孕期建议保留并列入核对；按实际分娩日期生成适用的产后建议 |
| 已开始或历史建议 | 保留；如有冲突，提示核对 | 未完成者提示核对，不自动完成或删除 |
| 已完成/已忽略事项 | 保留 | 保留 |
| 医院确定的预约 | 日期保持；若与关联的新窗口冲突，提示联系医院 | 保留原预约；孕期未完成预约提示核对 |
| 手动个人事项 | 默认保持；只有用户明确选“随孕周移动”的未来事项才移动 | 保留，相关孕期事项提示核对 |
| 健康记录/备忘 | 记录发生日期保持 | 保持 |

- 稳定编号由“孕程 ID＋模板 ID”组成，同一个孕程重复计算不重复生成。一个孕程和未来宝宝资料分开关联，便于以后增加宝宝一周岁前的内容。
- 每条临床模板包含适用地区、人群、时间锚点、窗口、来源、核验日期和审核状态。未核验或不适用的模板不自动生成医疗日程。
- 日期使用年月日进行整天计算，不把本地午夜当成国际时刻换算；跨时区不会把既有事项改到前一天。预约保存当地日期/时间及可选时区，详情中显示原预约时区。
- 超过预产期只提醒核对；不推断已生、不改年份。异常久远或未来资料不显示误导性孕周。
- 手动切换产后但未填出生日期，可显示“产后，待补日期”，不编造产后天数。实际分娩日期不得是未来日期。
- 临时住院等情况由用户手动添加事项、更新阶段或录入医生安排，不从体重或血糖读数推断。
- 日期修改历史与临床模板更新历史分开，前者不能被后者覆盖。批量改动进入过去时保留原日期并核对，不静默挪到今天。

## 5. 数据保存与旧数据迁移

已确认首版使用本机保存，页面持续显示“仅本机保存”。数据、旧资料迁移与备份恢复已接入页面；没有云端登录或同步，不覆盖旧存储键。

| 方案 | 使用方式 | 成本与限制 |
| --- | --- | --- |
| 沿用本机保存 | 无需登录；同一网址、同一浏览器保留数据；手动导出/恢复换机 | 不新增数据库费用；浏览器清理、无痕模式、设备损坏会丢数据，不保证永久保留 |
| 首版登录同步 | 以个人登录身份访问私有数据库；换手机重新登录访问 | 增加鉴权、访问隔离、账号恢复、同步冲突及服务备份验证；费用取决于服务和配额，选型后再核实 |

若选择云端，保留现有静态前端，增设最小登录和私有存储接口；核实当前 Netlify 资源后再选服务，不先锁定额外技术栈。健康记录需要服务器端验证用户身份并限制本人访问。仅前端隐藏、公开 JSON、简单 PIN 或站点密码均不能替代数据访问隔离。真正的密钥只能留在服务端环境配置中。

### 迁移顺序

1. 在原设备、原网站读取旧键原始内容。读取/解析失败时保留原值，显示恢复入口；不能自动空白覆盖。
2. 先把旧数据原样备份到本机独立备份键，并提供下载备份。备份写入失败则中止迁移。
3. 展示记录天数、饮食/活动数据、旧计划、自建知识等清单，再生成新结构副本。旧计划放入“旧资料”，不转换为医疗预约；GL 不转为血糖；缺失时间不捏造。
4. 在新存储键或事务中写入并校验；成功后启用新版。旧键保留。失败可回到原记录，不能先删旧数据。
5. 导入恢复先校验格式/版本/日期/数值，展示影响清单并备份当前数据。首版优先提供明确的“替换恢复”，不声称支持尚未实现的跨设备自动合并。
6. 云同步若采用，第一次上传旧数据前单独显示将上传的数据量和范围。不能将所有浏览器资料悄悄传到云端。

JSON 备份会包含私人健康资料，应存到用户自己的安全位置。前端/README 不承诺“加到主屏幕就永远不会清理”。备份需要实际恢复测试；导出动作无法保证用户已长期妥善保管文件。

Netlify 草稿网址、生产网址、GitHub Pages 网址各自有独立浏览器存储空间；预览页看不到旧记录不代表记录消失。手机跨浏览器、主屏幕应用与浏览器的存储隔离也应以实测为准。
